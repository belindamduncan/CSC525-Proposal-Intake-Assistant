Project Overview
The Proposal Intake Assistant is a Python application built with Streamlit to help collect preliminary requirements for industrial automation projects. Customers describe their projects in everyday language, and the application predicts a project category, identifies technical requirements, and generates a preliminary proposal.

The project combines a trained machine learning classifier, natural language processing (NLP), and Python rules. It is a proof of concept for gathering initial requirements, not a replacement for technical discovery or a final engineering proposal.

Tools and Technologies
Python: Application logic and data processing.
Streamlit: Chatbot interface and conversation history.
scikit-learn: TF-IDF text features and Logistic Regression classification.
Joblib: Saving and loading the trained model and vectorizer.
spaCy and PhraseMatcher: Identifying technical terms in customer messages.
JSON: Storing the technical vocabulary and proposal wording.

TF-IDF (Term Frequency–Inverse Document Frequency) converts text into numerical features. Logistic Regression uses those features to predict the type of customer project. The spaCy component uses predefined vocabulary to extract requirements; it is not a separately trained machine learning model. The proposal is assembled from JSON templates rather than generated by a large language model.

How the Application Works
1. The customer enters a project description in the chatbot.
2. TF-IDF and Logistic Regression classify the message as Historian and Visualization, Cloud Data Sharing, or Source Connectivity.
3. spaCy identifies known equipment, quantities, communication protocols, and data destinations.
4. Streamlit session state saves the conversation and accumulates requirements across messages.
5. Python rules build a response and ask for a data destination if one has not been provided.
6. The proposal generator fills JSON templates with the collected information.

The classifier evaluates each new message separately, while the extracted requirements are retained across the conversation.

Model Training and Results
The training dataset contains 90 fictional customer requests, divided evenly among three categories: historian_visualization, cloud_data_sharing, and source_connectivity.

The model uses TF-IDF features, including two-word combinations (bigrams), with Logistic Regression. A stratified 80/20 split provided 72 training examples and 18 test examples.

Test accuracy: 72.22% (13 of 18 predictions correct).

This result demonstrates that the classifier learned useful patterns from the small dataset, but it does not establish production-level accuracy. A larger and more varied dataset would be needed to evaluate performance on unfamiliar customer requests.

The trained classifier and its TF-IDF vectorizer are saved with Joblib so the application can use them without retraining each time it starts.

Application Testing
The main workflow was tested using two consecutive customer messages.
Message 1:
We need to connect 40 power meters using Modbus TCP and collect their operational data in AVEVA PI.

Message 2:
We also have 10 PLCs using OPC UA.

After both messages, the application retained:
Equipment: 40 power meters and 10 PLCs.
Communication protocols: Modbus TCP and OPC UA.
Data destination: AVEVA PI.

Predicted category: Source Connectivity for both messages.
The application also displayed the four preliminary proposal sections: Executive Summary, Project Scope and Objectives, Discovery Requirements, and Identified Technical Requirements.

This confirmed the main workflow, including classification, NLP extraction, conversation memory, and proposal generation. It was not a complete test of every possible customer request.

Challenges and Lessons Learned
Recognizing equipment names: The initial NLP matcher recognized “power meters” but missed “PLCs.” Changing the equipment matcher to use LOWER and adding singular and plural terms to the vocabulary allowed both examples to be recognized. This showed how matching rules and vocabulary choices affect NLP results.

Remembering previous messages: Streamlit reruns the script during user interactions. Session state was needed to retain customer messages and requirements across the conversation.

Separating the project components: Using different Python files for training, requirement extraction, proposal generation, and the chatbot made troubleshooting easier. It also helped distinguish trained machine learning from rule-based processing.

Using the same TF-IDF vectorizer: New customer messages must be transformed with the vectorizer saved during training so the classifier receives the expected features.

Limitations and Future Improvements
The application is a course prototype with several limitations:

#The classifier uses a small fictional training dataset and may misclassify unfamiliar requests.
#The NLP extractor only recognizes terms and variations included in its vocabulary.
#Equipment quantities are detected when a number appears immediately before a recognized equipment term.
#The application collects equipment and protocols but does not link each protocol to a specific piece of equipment.
#Project categories are predicted for individual messages, not the entire conversation.
#The proposal templates cannot confirm technical feasibility, pricing, network requirements, or final project scope.

Future improvements could include more training examples, expanded technical vocabulary, better quantity extraction, equipment-to-protocol mapping, and additional testing.

Running the Application
Open a terminal in the project folder and install the required packages:
1. python -m pip install streamlit scikit-learn joblib spacy
2. python -m spacy download en_core_web_sm

Start the application:
python -m streamlit run app.py

The chatbot should open in a browser. The saved model, vectorizer, vocabulary file, and proposal templates must remain in their project folders.
